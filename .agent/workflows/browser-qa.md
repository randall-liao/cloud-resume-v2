# Two-model browser QA

Run this workflow with `npm run qa:live` from the repository root. The command selects `github-copilot/gpt-6-astra`; `.omp/agents/browser-operator.md` selects `github-copilot/gpt-6-luna` for browser execution. Use normal execution mode, not omp's read-only plan mode.

## Astra orchestration contract

1. Read `infra/local-dev/agent-harnesses/live/RUNBOOK.md`. Respect a user-requested subset; otherwise select every case listed there. Do not invent requirements or expand into app changes.
2. Check prerequisites with `npm run browser -- --version` and an HTTP request to `${E2E_BASE_URL:-http://localhost:8080}/healthz`. Do not rebuild/restart an already healthy host unnecessarily. If the tool, model or host is unavailable, record the exact blocker rather than substituting a model or browser backend; still create the requested inventory in step 3 and finalize in steps 8–9 before reporting.
3. Create a unique run ID, select the intended cases, and state each case's acceptance criteria. A case's `caseId` is its source markdown filename without `.md` (for example, `mobile-resume.md` → `mobile-resume`). Use an evidence directory `temp/e2e-evidence/live/<run-id>/<caseId>` and a unique short session name per case. Pass the base URL explicitly. Before delegation, write an initial `summary.json` with `requestedCases: [{caseId, caseFile}]` for **every** requested case and `cases: []`; `caseFile` is the repository-relative intent markdown path. Retain the run/model/base-URL metadata described below. This inventory must survive unavailable workers and routing/prerequisite failures, not just successful cases.
4. Delegate each complete case to the named `browser-operator` agent with `schemaMode: strict`, one case at a time. Include the case file, criteria, base URL, session name, evidence directory, 40-command limit and five-minute limit. Require screenshot checkpoints, video-start and tracing-start before first navigation, and video-stop/tracing-stop before closing, including failure cleanup. Reserve time for capture finalization. Use `solutionSpace` to specify browser execution and evidence only, with no repository edits. Do not delegate to the generic task/sonic agent or infer that `smol` means Luna.
5. Remain the planner/reviewer. Do not operate a browser, replay each action in your own context, or call a second autonomous browser framework. Wait for each operator result before starting the next case. Browser delegation is the execution work, not an optional suggestion.
6. Verify the runtime worker model where the harness exposes it. If it is not `github-copilot/gpt-6-luna`, stop and report the routing mismatch; configured model selectors can be superseded by user overrides or provider fallback.
7. Review the structured results and evidence paths. Inspect targeted failure screenshots or contradictory observations as needed, not every intermediate snapshot. Do not convert blocked/failed into passed, remove assertions, skip failing tests, or silently retry through a product defect.
8. Update `temp/e2e-evidence/live/<run-id>/summary.json` after each worker and at termination with `{runId, requestedCases: [{caseId, caseFile}], cases: [operatorResult]}` plus requested planner/operator model IDs and base URL. Retain the entire original requested inventory even if a case fails, is skipped or never starts. Keep operator results in their existing schema (`caseId`, `status`, `assertions`, `evidence`, `reproduction`, `blocker`). Include actual model/usage metadata only when supplied by the runtime, never invented. Record top-level worker failures as blocked results with an explicit blocker; if no result can be recovered, leave that case absent from `cases` but present in `requestedCases`, so the packager creates a blocked package. Preserve failed assertions and missing evidence, never fabricate captures.
   Record observed command counts and worker duration when available. Report overruns of the prompt-based case limits as workflow deviations even when application assertions pass; never present those limits as enforced billing caps or substitute browser-only time for whole-worker time.
9. As planner, always run `npm run qa:package -- temp/e2e-evidence/live/<run-id>` after saving the summary, including failed/blocked runs and prerequisite/routing stops. Do not delegate packaging to the operator. The command copies exact case intent into `case.md`, writes a self-contained `<caseId>/index.html` and `result.json`, and creates the run `index.html` and `manifest.json`. Screenshots, video and complete trace artifacts are mandatory; absent captures produce explicit `missingEvidence`/incomplete evidence, a blocked package when no result exists, and a nonzero packaging exit without discarding review pages. Keep raw assertion status separate from evidence completeness. If the planner is externally interrupted, resume finalization with the saved summary rather than dropping requested cases.
10. Report a compact case/status/evidence-completeness table, observed failures and any model-routing discrepancy. Link the obvious run review page `temp/e2e-evidence/live/<run-id>/index.html` and failed/blocked case pages (mobile: `<run-id>/mobile-resume/index.html`); reviewers should not have to hunt cryptic capture filenames. Suggest deterministic regression changes for new durable findings; do not modify code or create a PR in a QA-only run. Passing live cases do not establish that the separate deterministic suite or CI passed.
